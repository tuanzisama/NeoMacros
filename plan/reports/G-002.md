## 2. 事件设计

### 2.1 目录与既有机制核对（现状即用，无需新建机制）

| 机制 | 现状 | packet 用法 |
| --- | --- | --- |
| 事件登记 | `ProductionEventSet.records()` 显式清单 + `EventCatalog.register`（`@ApiEvent` 驱动） | 新增两条 record 进清单；`packet` 成为内建域后，自定义事件不可再占用该域（EventCatalog 现有保护） |
| 通配忽略 | `EventBus.DEFAULT_WILDCARD_IGNORES` **已含 `packet:*`**（代码真源） | 13 号 §10.4 所述"packet 进高流量忽略名单"已就位；`events.on('*')` 永不收到 packet 事件，精确名订阅不受影响 |
| 可取消语义 | `cancellable=true` ⇔ 可 `onSync` ⇔ 回调 truthy/`cancel()` 取消（唯一语义） | 仅 `packet:send` |
| 改写语义 | `@ApiEvent(mutable={...})` 白名单 → `envelope.hooks().write` → `PublishResult.verdict` | `packet:send` 的 `mutable={"buffer"}`（字段替换通道）；缓冲区**原地改写**走 cell 本身，不经 hooks（见 §4.6） |
| 字节跨界 | `Payloads.snapshot` → 引擎 `__neoBytes` → JS `Uint8Array` | `PacketBuffer.readBytes()` 等返回 `Uint8Array` |
| 类跨界 | `ScriptHandle` + `@ApiClass` → `guestHandle` → 真实 ES 类实例 | `PacketBuffer implements ScriptHandle`，sync/async 两条通道拿到同一 host cell |

### 2.2 `packet:receive`

```java
@ApiSince("0.7.0")            // 以 G-031 开工时最新 ApiSince 基线为准
@ApiMC(">=1.21.6")
@ApiLoader("*")
@ApiEvent(name = "packet:receive", direction = ApiEvent.Direction.S2C, cancellable = false)
public record PacketReceiveEvent(String id, String flow, String protocol, PacketBuffer buffer) { }
```

- **方向**：`S2C`（服务器下行内容落地前的观测点），符合 `ApiEvent` 不变量 `cancellable ⇔ direction != LOCAL`。
- **可取消性**：**不可取消（维持 12 号 §5.3 拍板 `✔（send）`）**。推荐理由：(a) 12 号已拍板；(b) 收包钩子在 netty 线程，取消需要跨线程会合（§7.3），阻塞网络线程的风险与收益不成比例；(c) 任意丢弃下行包会破坏客户端（keep-alive 不应答→被踢、区块缺失→鬼影）。**若需求方要 JsMacros parity，备选方案见 §14 拍板②**（可取消 + 永不可取消的保护类名单 + 有界会合），改变 12 号拍板。
- **payload 字段**（`id`/`flow`/`protocol` 取值均来自 Mojmap 公有 API，§7.1 已证）：

| 字段 | 类型 | 取值 | 来源 |
| --- | --- | --- | --- |
| `id` | `string` | namespaced 官方包 id，如 `minecraft:keep_alive`（12 号 §5.3 的 `id`，细化为 string，回写点） | `packet.type().id().toString()` |
| `flow` | `'clientbound'\|'serverbound'` | 包自身流向 | `packet.type().flow()` |
| `protocol` | `'handshaking'\|'status'\|'login'\|'configuration'\|'play'` | 连接当前协议阶段 | `packetListener.protocol().id()` |
| `buffer` | `PacketBuffer \| undefined` | 无独立编解码器（含 bundle）时**缺席 = `undefined`** | 按需重编码，§4 |

- **不设 `type` / `direction` 字段名**：`BaseEvent` 原型已占用 `type`（事件名）、`direction`（事件流向）、`timestamp`、`cancellable`，payload 同名 own-property 会遮蔽原型语义（引擎 `__neoWrapEvent`/`__neoWrapMutableEvent` 机制核对过）；包流向字段因此命名 `flow`（Mojang `PacketFlow` 原词）。JsMacros `event.type` → compat 桥接映射到 `event.id`（compat 侧归 G-004/G-005）。
- **触发点与顺序**：`Connection.channelRead0` HEAD（netty 线程）→ hub 过滤（§3）→ `Minecraft.execute` 迁主线程发布（先于 vanilla `ensureRunningOnSameThread` 入队，同 tick 内、**先于包处理执行**）。异步通道是唯一通道（不可取消 ⇒ 无 onSync）。
- **bundle**：`channelRead0` 看到的 bundle 形态（delimiter/子包/整包）两代实现需真机确认（§8.5-10）；无论哪种，bundle 类无独立编解码器 ⇒ `buffer: undefined`，与 JsMacros"bundle 作为单包报告且无 buffer"的口径一致。

### 2.3 `packet:send`

```java
@ApiSince("0.7.0")
@ApiMC(">=1.21.6")
@ApiLoader("*")
@ApiEvent(name = "packet:send", direction = ApiEvent.Direction.C2S,
        cancellable = true, mutable = { "buffer" })
public record PacketSendEvent(String id, String flow, String protocol, PacketBuffer buffer) { }
```

- **方向**：`C2S`（上行动作拦截：包尚未上线）。**可取消**：onSync 回调 truthy ⇒ 该包不发送（`ConnectionMixin` 处 `ci.cancel()`）。
- **线程**：钩子先判断 `Minecraft.isSameThread()`——
  - 主线程（游戏逻辑、脚本经 facade 已迁主线程的发送、以及绝大多数 vanilla 发送）→ **内联同步派发**（与 `inventory:click`/`chat:send` 同款语义，SyncWatchdog 500ms 预算生效）；
  - 非主线程（netty/工作线程偶发直发）→ **整个发送推迟到主线程执行**（`Minecraft.execute(() -> 真实 send(...))`），回调下轮主线程泵再走内联路径。**不阻塞网络线程**（主线程可能卡在 GL/IO，会合方案有 keep-alive 连锁风险）。备选"有界会合"见 §7.3。
- **改写**：见 §4.6——同步通道内 cell 原地写 + `mutable={"buffer"}` 字段替换；同步派发结束后 adapter 对（最终）cell 重解码，命中则经 `@ModifyVariable` 替换出站参数，解码失败 **fail-open（原包照发 + warn 日志）**（§4.5）。
- **多脚本语义**：字段替换按优先级 last-write-wins（EventBus 现有合并规则）；原地写是同一个 cell，天然共享。

### 2.4 与既有拦截器的次序（文档必须写清）

```text
发包：脚本/游戏 → ClientPacketListener.sendChat（chat:send 裁决）
                    → ClientCommonPacketListenerImpl.send（inventory:dropSlot 裁决，DropPacketMixin）
                    → Connection.sendPacket（packet:send 裁决/替换）→ 上线
```

- `inventory:click` / `inventory:dropSlot` / `chat:send` 取消 ⇒ 其包根本到不了 `packet:send`（前级已吞）；反之 `packet:send` 是最后一道闸。
- 脚本自建发送（`client.sendPacket` / `buffer.send()`）同样经过 `packet:send`（与 T-524"手动与脚本同路"一致），即脚本可观察/取消另一个脚本的发送。
- 收包：`packet:receive` 发布先于 vanilla 分发 ⇒ 订阅者观测顺序 = 线上顺序。

## 3. 包过滤（高流量忽略）

三层，各管一件事，配置面分开：

| 层 | 作用点 | 机制 | 状态 |
| --- | --- | --- | --- |
| L1 通配忽略 | EventBus 分发时 | `DEFAULT_WILDCARD_IGNORES` 含 `packet:*`；`CoreOptions.wildcardIgnoresExtra` 追加 | **已就位**（13 号 §10.4 达成项，12 号 §5.4 表述与代码有漂移，见 §13 回写） |
| L2 发布前抑制 | `ConnectionMixin` → `PacketHub`（adapter） | 按 `id`（namespaced）匹配抑制名单：命中则**完全不发事件**（payload 都不构造） | **新设计** |
| L3 订阅内过滤 | 脚本回调 | payload 极廉价（id/flow/protocol 标量），`buffer` 懒物化；脚本自行 `if (e.id !== ...)` | 既有能力 |

**快路径（性能关键）**：L2 之外，core 侧 `PortEventWiring` sink 在构造 payload 前先问 `bus.hasDispatchTarget("packet:receive")`（新 API：精确订阅存在 ∪ 未被忽略的通配订阅）。零订阅时整条链退化为一次 Set 查找 + 一次 boolean 分发——忙碌服务器每秒上千包也不产生分配。

**L2 默认名单（推荐，`需需求方拍板` 可调——见 §14 拍板③）**：

```text
packetIgnore 默认 = [
  "minecraft:bundle_delimiter",          // 帧分隔（1.21.6/26.x 两代均有 BundleDelimiterPacket，真机核对最终 id）
  "minecraft:move_entity_pos", "minecraft:move_entity_pos_rot",
  "minecraft:move_entity_rot", "minecraft:rotate_head",        // 下行实体移动族
  "minecraft:set_entity_motion", "minecraft:entity_position_sync", "minecraft:teleport",
  "minecraft:move_player"                                      // 上行玩家移动（20/s 恒定流）
]
```

选择依据：只吞**帧级/恒定高频且脚本已有等价观测面**（移动族另有实体状态与 movement 事件可观察）的包；keep-alive、chunk、entity-metadata 等保留（频次低或诊断价值高；buffer 懒物化保证大包无订阅成本）。具体名单以真机 profiler 复核（§8.5-11）。

**用户扩展点**：
- `CoreOptions.packetIgnore: List<String>`（新增字段，config.json）——**显式设置即整体覆盖默认名单，`[]` = 全放行**；与 `wildcardIgnoresExtra`（追加式）刻意不同：抑制名单需要"关掉默认"的能力。adapter 经现有先例（`FabricCommandPort` 等已 import core）直接持有 `CoreOptions` 引用，volatile `Set` 缓存，运行时改配置即生效。
- 通配层扩展沿用 `wildcardIgnoresExtra`，不动。

## 4. PacketBuffer 生命周期

### 4.1 形态与归属

- `core/api/types/PacketBuffer.java`：`@ApiClass(name = "PacketBuffer", kind = HANDLE, wraps = "net.minecraft.network.FriendlyByteBuf")`，`implements ScriptHandle`，挂 `neo` 根（`new neo.PacketBuffer()` 与 `client.createPacketBuffer()` 双入口，§4.8 惯例）。
- **三种来源，一套实现**：

| 来源 | 构造点 | 编码器 | 写权限 |
| --- | --- | --- | --- |
| send-event cell | `PortEventWiring` 构造 payload 时（包住 `PacketRef`） | `port.encodePacket(raw, protocol)` 懒调用 | 同步派发窗口内可写（§4.4） |
| receive-event cell | 同上 | 同上 | **只读视图**（写一律抛错） |
| builder | `client.createPacketBuffer()` / `new PacketBuffer()` | 无来源，空缓冲 | 恒可写 |

- **所有权**：cell 是事件作用域句柄——事件内有效是"写窗口"语义（§4.4），不是资源释放语义；cell 不持有池化 `ByteBuf`（内部 `byte[]` 堆拷贝），无泄漏面，取消/异常路径无需释放。
- **payload 冻结与 cell 可变不冲突**：record 字段引用不可重绑（冻结），cell 内部是刻意的可变单元；引擎把 host cell 直接交给 guest（`Payloads.snapshot` 对未知对象透传 + `ScriptHandle` → `guestHandle` 路径），sync/async 订阅者拿到**同一 host 对象**——这是原地改写能被 adapter 看见的前提。

### 4.2 读写指针语义（ByteBuf 对齐，命名沿 Mojang/netty 动词）

- `readerIndex` / `writerIndex` **属性**（无参状态属性化铁律）只读；改用方法 `setReaderIndex(i)` / `setWriterIndex(i)` / `setIndices(r, w)` / `resetIndices()`。
- `markReaderIndex()` / `resetReaderIndex()` / `markWriterIndex()` / `resetWriterIndex()` / `clear()` / `skipBytes(n)` 原词保留（netty 标准动词，非 JsMacros 俗名）。
- `reset()`（JsMacros 语义）：**恢复编码时捕获的初始字节与初始指针**——收/发事件 cell 物化时即捕获；用于"读一遍再重新解码"的 JsMacros 典型用法。注意 JsMacros javadoc 里写的是"恢复读位置"、实现是字节+指针双恢复，以实现为准写文档。

### 4.3 编码语义

- `buffer` 物化 = 用该包类当前协议阶段的**独立编解码器重编码**（`STREAM_CODEC` 静态字段反射定位，两代均在，§7.1），得到 canonical 字节，**不是原始 wire 字节**（varint 宽度/可选字段规范化）；字段顺序与 codec 读写顺序一致，读改写回环稳定。
- 缺席：无独立编解码器（bundle、个别无 codec 包）→ payload `buffer = undefined`（对应 JsMacros `canGetPacketBuffer()`，§6 判 A）。
- `toPacket(name?, protocol?)`：从当前 `readerIndex` 起解码（缺省 = 来源包类/来源协议；builder 缺省 play）。**返回 `JavaObject` → `@ApiPermission("java")`（单闸拍板⑥⑦）**。
- 重编码失败（编解码器在、注册表缺席等）→ 抛 `Error('packet buffer encode failed: <cause>')`，响亮失败（失效语义 §2.6 规则 4）。

### 4.4 有效窗口与"事件后失效"

| cell | 物化后读 | 事件结束后读 | 任何时刻写 |
| --- | --- | --- | --- |
| send-event | ✔ | ✔（字节是堆拷贝，永续可读） | 窗口内（同步派发期间）✔；窗口关闭后**抛** `Error('packet buffer is read-only after the packet:send event')` |
| receive-event | ✔ | ✔ | **一律抛** `Error('packet buffer is a read-only view (packet:receive)')` |
| builder | ✔ | 不适用（无事件） | 恒 ✔ |

- **窗口关闭由 adapter 驱动**：`ConnectionMixin` 在同步派发返回后立刻关闭（重解码→替换/放行→close，同一次主线程调用栈内）。关闭操作与 cell 读写同一把锁（cell 内 `synchronized` + volatile 状态位）：async 订阅者的写要么完整先于关闭（并入本次替换，可接受且确定），要么落进关闭之后抛错——**无数据竞争**。
- 明确**不设"读过期"**：async 通道在 publish 之后才执行（EventBus 先同步后排队 async，已核代码），若读也过期则 `events.on('packet:send')` 全部无法用 buffer——所以失效只针对"改写能否上 wire"，读永续。d.ts 与事件页必须写死这句："事件回调外，缓冲区可读不可写"。
- receive cell 长期持有来源包 POJO（大包如 chunk 的对象图）——文档提示"用完丢引用，长留会拖住对象图"（JVM GC 可回收，无 native 泄漏）。

### 4.5 失败语义汇总（任务卡验收项）

| 场景 | 语义 |
| --- | --- |
| 无独立编解码器 / bundle | `buffer = undefined`（缺席，不抛） |
| 重编码抛错 | 物化处 `throw Error(...)`（响亮） |
| send 改写后重解码失败 | **fail-open：原包照发 + adapter warn 日志 + 诊断计数**（网络完整性 > 脚本意图；取消是显式语义，坏字节不是） |
| 字段替换 cell 与原包类不匹配 | 同上 fail-open（v1 只支持同包类改写，换类 = `replacePacket` 归 D，§6.3） |
| sync 回调内脚本异常 | 既有 SyncWatchdog 行为（超时禁用该订阅；异常隔离按现状），不为 packet 单开路径 |
| 越窗写 / receive 视图写 | `throw Error(...)`（§4.4 文案） |
| 事件后读 | 正常返回字节 |

### 4.6 改写通道与 verdict 的交互

```text
onSync 回调 ──原地写 cell（writeXxx…）────────────┐
           └─hooks.write("buffer", otherCell)───┤→ verdict Map（last-write-wins）
                                                │
publish 返回 → PortEventWiring 取 verdict["buffer"] ?: 原 cell
            → cell.dirty() ? port.decodePacket(id, protocol, cell.bytes) : null
            → PacketSendVerdict(canceled, replacementRaw)
            → mixin：canceled ⇒ ci.cancel()；replacementRaw ⇒ @Unique 槽位
            → @ModifyVariable(sendPacket, LOAD, argsOnly, ordinal=0) 换参
```

- 原地写**不产生 verdict 条目**（hooks 只捕获字段写），所以 adapter 判据是 `cell.dirty()`（写操作置位），不是 verdict 有无——两者合并判断：`最终cell = verdict 有替换 ? 替换cell : 原cell`，再问它的 `dirty()`。
- 替换 cell 是 builder（无来源）时按事件原包类解码（v1 规则，§4.5）。

## 5. send 信任门（**需需求方拍板**）

### 5.1 与 T-100 的衔接（现状机制原样复用，零新机制）

- T-100：`TrustManager.CAPABILITIES = {"fs","net","command","java"}`；脚本 manifest `permissions` 声明 → 内容哈希信任（`viewFor`）→ `PermissionView` → `ModuleBinding` 把 `@ApiPermission(k)` 成员包成 `DeniedMember`（可见、调用即 `PermissionError`，信息提示"not declared in this script's meta.permissions"）→ 首次声明且未信任时弹 `logClickable` 信任提示。
- packet 门 = 给少数成员打 `@ApiPermission(...)` + （方案甲）向 `CAPABILITIES` 加一个键 + 12 号 §4.19 目录 + 文档；**API 实现层不复查权限**（ApiPermission 契约）。

### 5.2 方案（推荐甲）

**甲（推荐）：新增能力键 `packet`** —— "`permissions:['packet']` = 授权把任意字节放到游戏连接上"。
- 与 `java` 分工：`java` 门"拿到/操作任意宿主对象"（`client.minecraft`、`buffer.toPacket()`、`client.sendPacket(JavaObject)` 的实参本身非 java 不可得）；`packet` 门"无 java 对象也能造包上 wire"的窄面（`buffer.send()`：cell 字节 → adapter 内部解码 → 发送，脚本边界全程不出现 raw 对象）。
- 这使"只想发包、不想交出整台机器"的脚本可以只声明 `packet`——可解释、可审计的窄授权；与 12 号 §4.0 现状（`sendPacket` 需 `java`）不冲突，是叠加而非推翻。

**乙：不新增键** —— `buffer.send()` 也标 `java`（原始包发送统一并入穿透层单闸，`CAPABILITIES` 不动，改动面最小；代价是"发包"与"访问宿主"两种意图绑死，且 12 号 §4.0 无需改口径）。

**丙：免门控** —— 对齐 12 号 §4.19 免门控清单的论证（`inventory` 写、`input` 模拟、`chat.say` 均免门：替玩家操作是宏模组核心用途，清单信任门已是整体闸）。发原始包强度高于既有免门面（可构造客户端原本不会发的包），不推荐，但属需求方价值判断。

### 5.3 门控矩阵

| 成员 | 甲 | 乙 | 丙 |
| --- | --- | --- | --- |
| `client.createPacketBuffer()` / `new PacketBuffer()` / buffer 读写 / `reset`/索引 | 不设门（纯数据） | 不设门 | 不设门 |

### 7.3 线程策略（决策点）

- 收：netty 线程只做"过滤 + `Minecraft.execute(发布)`"，脚本回调在主线程泵内先于包处理执行（§2.2）；**网络线程零阻塞**。
- 发（主路径）：主线程内联同步派发（裁决就地返回，`ci.cancel`/`ModifyVariable` 生效）。
- 发（非主线程，罕见）：**推荐甲=推迟**（整次 send 挪主线程，回调再走内联；不阻塞任何线程，代价是多一轮泵延迟 + 跨线程发送间顺序按入队序）。**备选乙=有界会合**（网络线程等主线程裁决，预算 = `maxSyncTime`，超时 fail-open 放行）——与 JsMacros 时序最接近，但主线程被 GL/IO 卡住时会顺带卡住网络线程（keep-alive 风险），故列为备选。

10. bundle 行动观察（§7.4 决策输入）：两代客户端各抓一次 bundle 流，确认 `channelRead0` 形态与 `buffer: undefined` 行为，回填抑制名单 id。
11. 性能：繁忙服务器（实体 80+）对比三态帧时间/TPS——零订阅、精确订阅无过滤、`packetIgnore: []` 开；要求零订阅态与基线无可测差（快路径生效）。
12. 与既有事件共存：T-524 取消一次 `inventory:dropSlot` → 断言 `packet:send` 未收到该包（§2.4 次序）；改写聊天原文（`chat:send` 改写后再观察 `packet:send` 的 id/内容）。

## 9. 风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 性能：每包记录分配/发布 | 忙服务器每秒千级包 × 订阅链 | L2 抑制名单 + `hasDispatchTarget` 快路径（§3）；cell 懒物化（无订阅/未读 buffer 零编码成本）；8.5-11 实测门禁 |

| 同步派发拖住发包 | `packet:send` 回调超时拖主线程上行 | SyncWatchdog 500ms 既有预算（超时禁订阅）；文档要求回调短小 |
| 事件 bus 背压 | 收包发布进主线程队列的洪峰 | 发布在 netty 侧先过滤+快路径，进队列前已收敛；async 回调在执行器不占主线程 |
| 混淆/映射 | 26.x `Identifier` 更名、私有 `sendPacket` remap、1.21.6 obf 工具链 | §7.4 逐项：链式调用不落类型、loom remap、四节点 CI 首验（8.1-1） |
| 网络完整性 | 改写坏字节/越权丢包把连接打挂 | 改写 fail-open+warn（§4.5）；receive 不可取消（拍板②备选带保护名单）；`packet` 权限门（拍板①） |
| 线程 | netty 阻塞、跨线程写竞争 | 零阻塞策略（推迟而非会合，§7.3）；cell 单锁 + 窗口状态位（§4.4） |

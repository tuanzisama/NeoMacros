## ScreenPort 契约

- **分界**：屏幕**读面**留在 `LifecyclePort`（第六轮冻结，`screenInfo/screenTitle/closeScreen` 不动）；本端口只管**写面**（会话开合、控件变更、修饰键），与设计 §9 一致。
- **中立数据**：`ControlState`（14 字段快照）、`MouseInput(button,x,y,dx,dy,modifiers,doubleClick)`、`KeyInput(key,code,modifiers)`、`CharInput(character)` 内嵌 record——端口零 MC 类型、零 guest 类型。
- **SessionSink**（open 时注册）：`render(DrawContext2d,mouseX,mouseY,partialTick)` / `mouseDown|mouseDrag|mouseUp|keyPress|charTyped`（boolean = 消费，adapter 原样回传 vanilla "handled"）/ `controlEvent(id,event,payload)` / `stateChanged(id,state)` / `closed()`（会话终态，任意路径幂等恰好一次）。**adapter 永远只见中立数据，guest 函数不越端口**（回调全部由 facade 持有）。
- **主线程模型**：`open/close/reload/add/remove/write` 主线程跳（`MainThread.run`，失败/超时返回 null → facade 归一同步 throw）；**派发闸** `DISPATCH_DEPTH`（begin/end/isDispatchActive，深度计数可重入）——guest 回调执行期间主线程被停在 context loop 等待，闸内变更**内联跑**避免对停驻主线程的桥接超时（设计 §7.2「主线程再入」高风险项的落法：不依赖 `Minecraft.execute` 再入，改闸 + `isSameThread` 双条件）。
- **NONE 桩**：`NeomacrosAdapter.screen()` default 返回 `ScreenPort.NONE`——旧适配器零改动可编译；`open` 抛 `UnsupportedPortFeature` → facade 转同步可 catch 脚本错误（「打不开也不崩」的适配器缺位形态）。

## 生命周期 / Esc / 回调语义

**状态机**（设计 §6.1 落地）：

```text
buildScreen(spec) ──主线程跳 open（失败/超时 → 同步 throw，e2e 实证不崩）
   ▼
 open（displayed）── 任意路径 ──▶ closed（终态，回调恰好一次）
   │ ① Esc/closeOnEsc → onClose()          → closeIntent：回调 → 恢复父屏（returnTo='current'）或回游戏
   │ ② gui.close()    → 同 ①（先回调置 closed，port.close 只走回父屏）
   │ ③ 被其他屏替换   → removed() → replaced()：只发关闭通知，不回父屏（通知幂等）
   │ ④ owner 卸载     → LoadedModule.onRelease → dispatch闸内 port.close → 同 ①
```

- **回调与失效顺序**：`sessionClosed` 先派发 `close` 回调（此间读面存活、`closing` 闸挡重入），`finally` 才置 `closed`、清缓存——回调内再 `add/close` → throw（防重入）；二次 `closed()` 通知幂等（facade `closed||closing` 闸 + port `notified` 闸双层）。
- **单屏不变量**：`open` 时若当前屏是上一个脚本会话，先通知其关闭再开新会话，新会话继承其捕获的父屏（回调需要调用方 context loop，故通知放在主线程跳**之前**，跳内 `notified` 旗去重）。
- **Esc 链**（设计 §6.2）：vanilla `keyPressed` 首段 `shouldCloseOnEsc() → onClose()`；宿主覆写 `shouldCloseOnEsc`/`isPauseScreen` 读 spec。`super.keyPressed` 返回 true（Esc 已关屏 / 焦点控件 / 导航消费）则**不**进 sink；`closeOnEsc=false` 时 Esc 落到 sink，脚本可拦截自行 `close()`。鼠标/字符同链：控件（super）优先，屏级 sink 兜底，消费位逐级上抛。
- **回调执行模型**：全部同步、主线程（或派发闸内联）、`SyncWatchdog.guard` 限幅（超时仅节流日志）、异常吞掉 = 未消费。`onRender` 每帧在抽取期执行（预算文档：≤1ms）；`ScreenCanvas` 回调结束即 revoke。控件回调（`onClick/onChange`）与屏级输入/`close` 同模型。
- **状态双真源**：spec = 构建描述真源（port 持中立镜像），widget 实例 = 运行期真源；`clearWidgets`（resize/reload/add/remove 前）先 `adoptLiveState`（text/value/checked/locked）再拆树——窗口缩放与动态加控件不丢键入；`stateChanged` sink 回写 facade 缓存；`setControl` 同步就地写 widget + spec 镜像 + 缓存（白名单 8 键）。
- **事件**：零新事件类型；`screen:open/close/change` 由既有 per-tick 差分自动覆盖脚本屏（`kind='script'`，同屏 rebuild 不触发——差分按 `screenClass` 判变）。

## 任务卡外改动

### 重点审阅：`engine/GraalJsEngine.java`（+10 行，任务卡未列）

**改了什么**：`convertArgument`（handle 成员调用的入参转换）新增一个分支——参数类型是**函数式接口**且实参是 guest 函数时，走 `adaptFunction(argument, type)`（动态 Proxy 适配到声明接口）；`Consumer.class` 精确类型保持旧的 `asNeutral` 中立桥（`Object[]` 元组展开语义）。注释写明动机与保留项。

**为什么必需**：`BuiltScreen.on(String, Predicate<Object>)` 的参数类型是 `Predicate`（函数式接口）。改动前该路径落到 `asNeutral`——为 guest 函数返回 `Consumer<Object[]>` 桥，随后 `Method.invoke(handle, consumer)` 抛 `IllegalArgumentException: argument type mismatch`，即 **`gui.on` 必然失败**。module-binding 路径（同文件 `convertArgs`，早有 `type.isInterface() && value.canExecute() → adaptFunction` 分支，HostAccess.NONE 下的既有机制）与 handle 路径本应一致，此改动即对齐两者。

**证据**：① `BuiltScreen.on` 是 G-035 拍板④（运行期换回调）的唯一载体，e2e `ScriptScreenScenariosTest.callbackChains` 与 `script-tests/cases/g035-script-screen` 均以 `gui.on('mouseDown', …)` 为断言链的一环——无此改动两处必红；② 全量 `:core:test :e2e:test` 绿（538+70）；③ 改动前这些调用**本来就全部抛错**（failure→success 单向），不存在「行为翻转」面；④ 非接口类型、非函数实参、`Consumer` 精确类型三条路径逐字未动。

**风险评估**：影响面 = 所有 handle 成员的函数式接口入参（当前仅 `BuiltScreen.on`，未来 G-036+ 受益）；`Consumer` 子接口（非精确 `Consumer.class`）会改走 adaptFunction——现库无此类签名；Proxy 返回值按 void/boolean/object 三型归一（boolean 只认 `true`，JS falsiness 文档化）。**结论：实现必需，保留，不回滚**；已按任务要求显著披露。

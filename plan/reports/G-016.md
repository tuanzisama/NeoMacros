## 接线点说明（任务卡 `product/adapter/*Hub.java` 目标的定位结论）

两个事件的真实发布点都**不需要静态 hub**（hub 是 mixin 扇出的形态；本波两个源都不是 mixin 源），生产与 e2e 走同一条 `PortEventWiring` 单路径，语义不可漂移：

### W1 `game:resourcePack` —— 端口 sink 链

```text
Fabric API ResourceManagerHelper.get(CLIENT_RESOURCES) 重载监听器
  （FabricLifecyclePort.PackLoadedListener：Identifiable + vanilla ResourceManagerReloadListener
    双接口，onResourceManagerReload 落在重载 apply 阶段 = 游戏线程；getFabricId
    = neomacros:resource_pack_loaded；首个回调标记 isGameStart=true）
    → FabricLifecyclePort.resourcePackSinks（runSafely 逐个转发）
    → LifecyclePort.onResourcePackLoaded（新 default 方法）
    → PortEventWiring 订阅 → bus.publish("game:resourcePack", GameResourcePackEvent)
```

- e2e 注入：`StubLifecycle.fireResourcePackLoaded(isGameStart, loadedPacks)`（core 单测同款）。
- 监听器注册在 `FabricLifecyclePort` 构造期（mod init，先于初始资源重载），Fabric API v0 `ResourceManagerHelper` 是四节点唯一齐备的注册面（1.21.6 fabric-api 0.128.2 无 resource-loader-v1），新节点上该接口已标 `@Deprecated`，以 `@SuppressWarnings("deprecation")` 就地压制（接口本体仍存在于 3.3.27，四节点编译绿）。
- 覆盖：一切 CLIENT_RESOURCES 完成（启动加载、F3+T、资源包选择、语言切换、服务端包并入触发的客户端重载）；纯服务端数据包重载不触发（与 JsMacros"加载遮罩淡出"语义一致）。

### T1 `game:start` 时序关系（任务卡要求理清）

- NeoMacros `game:start` = Fabric `ClientLifecycleEvents.CLIENT_STARTED`，其 javadoc：**"This occurs while the splash screen is displayed"**——即启动重载**进行中**（遮罩还在）就已触发；`PortEventWiring` 在 `game:start` 发布前完成 `loadPhase(ALWAYS)`。
- 因此顺序恒为：`game:start`（ALWAYS 装载、订阅建立）→ 启动重载完成 → `game:resourcePack(isGameStart=true)` 到达已装载脚本。**无需缓冲/补发**（对比 JsMacros：其脚本引擎同样在启动期就绪，语义对齐）。
- `game:launch` 类前置事件与本事件无耦合；`isGameStart=false` 的后续重载在任意时刻直接发布。

### W2 `entity:customName` —— SelfStateTracker tick 差分（与 entity:damage/heal 同族）

```text
每 tick：adapter.entity().inRadius(玩家32格) 复用 health 轮询快照
  → 逐实体（含本地玩家）adapter.entity().entityState(uuid).get("customName") 取原始自定义名
  → lastCustomNames 差分（首见=基线、离场=清账）
  → 值实际变化才 bus.publish("entity:customName", EntityCustomNameEvent(uuid, old, new))
```

- 生产（fabric bootstrap）与 e2e 都经 `PortEventWiring.wire`，e2e 注入 = stub `setEntities` + `setEntityState` + `fireTick`（`ResourcePackNameChangeEventScenariosTest` 走此路径）。
- 不采用 JsMacros 的 `SynchedEntityData.assignValue` HEAD mixin：mixin 文件与 mixins.json 不在任务卡落点、`assignValue` 签名跨 1.21.6→26.3 需四节点 javap 逐一核对（`DataItem/DataValue` 泛型形态随版本变动）；tick 差分是本仓库既有单路径（G-014 `entity:damage/heal` 同款），零产品侧新增风险。覆盖差与升级路径见 L3。

## 高流量与去抖设计（任务卡要求）

`entity:customName`（逐实体同步理论上可高频——改名动画服务器逐 tick 翻名）：

1. **差分门控**：值未变不发布；服务器 no-op 赋值/同步回声全部抑制。事件率 = 实际改名率。
2. **首见基线**：实体进入半径/进世界首样只记不发，杜绝进入突发（沿 `entityHealth` 先例）。
3. **作用域限幅**：仅玩家在场 + 32 格半径（与 `entity:damage/heal` 同界），每实体每 tick 至多一条边沿。
4. **离场即忘**：出半径清账，回归重新基线，不重放陈旧名（沿 `entityHealth.keySet().removeIf` 先例）。
5. **通配抑制**：`entity:customName` 加入 `EventBus.DEFAULT_WILDCARD_IGNORES`（改名动画最坏 20 Hz/实体；精确订阅不受影响，`entity:*`/`*` 通配免淹）——既有 `entity:metadata` 预留位同族先例。**任务卡外一行改动**，12 §5.4 需回写。
6. **轮询成本面**：每 tick 每邻近实体一次 `entityState`（生产实现 = `entitiesForRendering` 线性 UUID 扫描 + 7 键 map），合计 O(m×n) 轻比较；既有 health 轮询本就每 tick 做 O(n) 全量扫描 + m 个 28 字段重快照，本增量同量级（量级估算 m=100/n=1000 ≈ 0.1–0.5 ms/tick）。若成热点，降采样（每 N tick）或升级 sync-path mixin（L3）二选一，接口面不变。

`game:resourcePack`：完成回调天然低频（每次重载一条），无去抖需求；`loadedPacks` 为触发时点复制的不可变列表（后续选择变更不回写）。

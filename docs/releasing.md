# Release channels & jar naming

Every distributable jar carries its channel in the version string, both in
the file name and inside `fabric.mod.json`, so an installed mod knows
exactly what it is running and the update checker can compare against the
right channel. The scheme is applied per product node in
`product/node-common.gradle.kts`; the baseline version lives in the root
`gradle.properties` (`version=0.1.0`).

## Naming

| Channel | Version string | Jar name (26.3 node) | Produced by |
| --- | --- | --- | --- |
| release | `0.1.0` | `neomacros-26.3-fabric-0.1.0.jar` | pushing a `v*` tag |
| dev | `0.1.0-dev.<build>+<sha7>` | `neomacros-26.3-fabric-0.1.0-dev.123+abc1234.jar` | every push to `main` |
| canary | `0.1.0-canary.<build>+<sha7>` | `neomacros-26.3-fabric-0.1.0-canary.45+def5678.jar` | manual workflow dispatch |
| local | `0.1.0-local` | `neomacros-26.3-fabric-0.1.0-local.jar` | any local Gradle build (default) |

Rules:

- `<build>` is the GitHub Actions run number, `<sha7>` the first seven hex
  digits of the commit — dev/canary builds order by the build number.
- The `fabric.mod.json` `"version"` field is stamped with the same string,
  so `FabricLoader` reports it and the mod can parse its own channel.
- Version-independent modules (core, ports, engine, doc-api) keep the plain
  baseline version; only the installable mod jars carry channels.

## CI triggers

| Workflow | Event | Channel |
| --- | --- | --- |
| `ci.yml` → `compile` | push to `main` | builds with `RELEASE_CHANNEL=dev`; artifacts attached to the run |
| `ci.yml` → `publish-dev` | push to `main` (after compile + unit pass) | rolls the `dev` prerelease tag, then dispatches `update-manifest` |
| `ci.yml` → `compile` | pull request | `RELEASE_CHANNEL=local`; run artifacts only, never published |
| `release.yml` | push tag `v*` | release channel; creates the GitHub Release with every node's jar + `SHA256SUMS` |
| `release.yml` | workflow dispatch (`channel: canary` or `dev`) | rolls the matching prerelease tag |
| `dev.yml` | nightly cron | verification only (tests + smoke), publishes nothing |

A release tag must equal the baseline version (`v0.1.0` ↔
`version=0.1.0`); the workflow fails fast on mismatch so clean-named jars
can never lie about their contents.

### Rolling prerelease tags

`dev` and `canary` are **rolling**: every publish deletes and recreates the
tagged release, so the URLs
`https://github.com/tuanzisama/NeoMacros/releases/tags/dev` and
`.../tags/canary` always point at the newest build while staying stable as
download entries (this is what the update manifest links to). Older MC
nodes' assets cannot linger because the release is recreated, not appended.

## Local builds

Without CI env vars a build lands on the `local` channel:

```bash
./gradlew :product:26.3:assemble    # → neomacros-26.3-fabric-0.1.0-local.jar
```

Local builds are deliberately unpublishable: the update checker never
auto-checks for them (manual `/neomacros update check` still works, and
compares against the release channel).

To fake a channel locally for testing, set the same env contract CI uses:

```bash
RELEASE_CHANNEL=dev BUILD_NUMBER=999 GIT_SHA=feed1234567890 \
  ./gradlew :product:26.3:assemble
# → neomacros-26.3-fabric-0.1.0-dev.999+feed123.jar
```

`RELEASE_CHANNEL` accepts `release`, `dev`, `canary` (the latter two
require `BUILD_NUMBER` and `GIT_SHA`); anything else fails the build.

## Update checker

The mod checks updates against its own channel (`core.update.channel`
defaults to `auto`: dev builds read the dev channel, local builds read
release). Prerelease builds additionally surface a newer stable baseline
once. Checks run on a dedicated thread every `core.update.intervalHours`
(default 12) and can be tuned or disabled in the settings screen
(`neomacros.config.category.update`) or `config/NeoMacros/config.json`:

```json
"update": {
  "enabled": true,
  "intervalHours": 12,
  "channel": "auto",
  "notifyInGame": true,
  "notifyEditor": true,
  "sources": [],
  "ignoredVersion": "",
  "lastNotified": ""
}
```

Commands: `/neomacros update check` (manual check), `ignore` (ignore the
latest finding), `clear-ignore`.

Notifications: an in-game toast + clickable chat card (release-notes link,
"ignore this version"), and an `update:available` SSE event to connected
editor panels, which show the top banner.

## Update data sources

GitHub is not reliably reachable from mainland China, so the checker walks
a source chain and takes the first payload that parses (custom `sources`
override the built-ins):

1. `https://neomacros.tuanzi.ink/update/updates.json` — the self-hosted
   manifest, generated by the NeoMacros-Docs repository's deploy workflow
   from the GitHub releases API and served alongside the docs site;
2. `https://api.github.com/repos/tuanzisama/NeoMacros/releases` — the
   GitHub releases list as a fallback adapter.

Both payloads normalize to the same channel map. The manifest contract:

```json
{
  "schema": 1,
  "updated": "2026-11-08T03:04:05Z",
  "channels": {
    "release": {
      "version": "0.1.0",
      "build": 0,
      "date": "2026-11-08T03:00:00Z",
      "notes": "https://github.com/tuanzisama/NeoMacros/releases/tag/v0.1.0",
      "files": [
        { "mc": "26.3", "url": "https://…/neomacros-26.3-fabric-0.1.0.jar", "sha256": "…" }
      ]
    },
    "dev":    { "version": "0.1.0-dev.123+abc1234", "build": 123, "…": "…" },
    "canary": { "…": "…" }
  }
}
```

- `channels` keys are `release|dev|canary`; an absent channel simply means
  "nothing published there yet" (the parser ignores unknown keys).
- `build` orders dev/canary entries; release entries compare by the
  `X.Y.Z` version.
- `files[].mc` matches the archive's Minecraft version segment.
- The generator lives in the docs repository
  (`NeoMacros-Docs/scripts/generate-updates.mjs`); every site deploy
  refreshes the manifest, and channel publishes trigger it immediately via
  the `update-manifest` repository dispatch (same secret as
  `docs-dispatch.yml`, skipped when the token is absent).

## Rolling back a bad release

Releases are immutable tags — do not rewrite `v*` tags. Publish a fixed
`vX.Y.Z+1` instead. A broken dev/canary build self-heals on the next
publish (the tag is recreated); to pull a bad rolling build immediately,
re-run `release.yml` with `workflow_dispatch` from a known-good commit.
